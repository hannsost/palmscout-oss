# First operator-owned accounts

Run **after migration 054**, before exposing the API. Use the reviewed API image
and its production configuration, with a one-shot process:

```sh
python -m app.operator_bootstrap --config-file /run/bootstrap/config.json
```

The argument is only a file path. The helper does not accept passwords in arguments
or environment values, send email, print identities/passwords/hashes, or seed demo
data. Mount the private input as a read-only Secret or private file outside Git.
Acceptable target permissions are `0600`, `0400` or group-readable `0440`/`0640`;
no world permissions or group writes. Projected Secret symlinks are supported.
The file owner must be the executing UID or root; maximum size is 16 KiB.

The exact JSON structure is version 1. Replace every descriptive placeholder in a
private file; this example is **not** an executable account fixture:

```json
{
  "version": 1,
  "tenant": {
    "name": "<operator-confirmed organization>",
    "slug": "<lowercase-slug>",
    "type": "internal_hr",
    "modules": ["kanban_pipeline", "interview_scheduling", "org_charts"]
  },
  "platform_admin": {
    "email": "<operator-confirmed platform owner email>",
    "full_name": "<operator-confirmed display name>",
    "password": "<privately supplied platform password>"
  },
  "tenant_admin": {
    "email": "<different operator-confirmed company owner email>",
    "full_name": "<operator-confirmed display name>",
    "password": "<different privately supplied company password>"
  }
}
```

Each password must have 16–72 characters and at most 72 UTF-8 bytes, with no control
characters. Accounts and passwords must differ. No credentials are generated by
the helper. Workspace types: `internal_hr`, `recruiter_agency`, `solo_recruiter`,
`zeitarbeit`. The initial module allowlist is exactly the three shown; an empty
list is valid. Provider-dependent modules are not automatically enabled. Later
module changes use the existing platform-admin controls after functional review.

The helper accepts only `APP_ENV=production` and an explicit PostgreSQL URL.
Production additionally requires explicit Redis URL, signing and scraper keys
(at least 32 characters), HTTPS frontend/CORS origins and disabled AI mock mode.
It uses the existing bcrypt password format. It creates atomically:

- one active tenant on the internal `free` plan (no Stripe subscription/trial);
- one platform administrator without tenant/company;
- one administrator of that tenant, linked to its company;
- two blank privacy-consent records (`ai_opt_in=false`, `terms_accepted=false`);
- only the explicitly requested initial modules.

The accounts are active and verified based on the operator's explicit identity
confirmation. This is **not a claim of email delivery or email-link verification**.
No SMTP, financial provider or external AI account is needed for this setup/login.

A single database transaction locks the identity tables, checks exact migration
054 and refuses an unrelated/nonempty initial identity database. Locks have a
5-second timeout. A second run checks both existing password hashes, roles,
tenant/company assignments and module configuration and returns
`bootstrap:already_initialized` without changing anything. Partial/colliding or
modified identities fail; this is not an account takeover/password-reset tool.
Failure messages contain only fixed codes; connection error details are suppressed.
Running it again after intentional account/module changes may correctly fail.

After a successful run, privately test both logins: `/users/me`, tenant owner
`/companies/mine` and `/users/workspace`, platform owner `/admin/customers`.
The tenant owner must receive 403 on platform-admin routes. Confirm the production
registration endpoint returns 403. Remove the one-shot Job and mounted setup
Secret after acceptance; preserve passwords only in the operator's approved
private password store. This helper does not remove Kubernetes resources.

Production `/auth/register` stays closed unless `PUBLIC_REGISTRATION_ENABLED=true`
is explicitly set. If later enabled, registration first creates a candidate;
verified company onboarding creates a separate tenant and a company admin.
The existing 14-day trial and module grants need separate review before opening
self-service registration. Enabling public production registration also requires
configured SMTP. A platform-admin account cannot convert itself into a company
account. Mail-based reset/verification return 503 before looking up any account
when production SMTP is unavailable; they do not pretend to deliver a link.
They are not the owner setup or recovery mechanism for this pilot.

Offline checks: `PYTHONDONTWRITEBYTECODE=1 python3 checks/backend-launch.py`.
These use synthetic state and mocked SQL; the operator must still run the actual
PostgreSQL transaction/replay/conflict and HTTP acceptance in isolation before
public exposure. No migration or bootstrap was executed during preparation.
